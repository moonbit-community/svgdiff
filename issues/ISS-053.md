## Description
Define independent compatibility and version-allocation rules for the MoonBit module, Structured Report schema, Diagnostic codes, and Domain Ordering policies.

## Design
Keep each compatibility domain independently identifiable. Use SemVer for the published MoonBit module, a major/minor report-schema identity for serialized interpretation, stable Diagnostic codes with unknown-code-safe consumers, and opaque versioned policy IDs for ranking tuples. Add a deterministic check that the current module, CLI, Schema, renderer-conformance profile, and ordering-policy identities remain synchronized across their authoritative surfaces.

## Acceptance Criteria
- [x] MoonBit pre-1.0 and post-1.0 compatibility rules are explicit.
- [x] JSON Schema version allocation distinguishes compatible additions from interpretation-breaking changes.
- [x] Diagnostic addition, removal, rename, and meaning changes have explicit consumer and producer rules.
- [x] Ordering-policy changes always allocate a new opaque policy ID and forbid cross-policy tuple comparison.
- [x] A release-review matrix states which identities must change for each contract change.
- [x] An executable test detects drift among the current authoritative version surfaces.

## Close Notes
Defined independent compatibility domains and allocation rules for the module/CLI, Structured Report, Diagnostics, ordering policies, and renderer conformance. The pre-1.0 module policy reserves minor increments for breaking changes and keeps patch releases backward-compatible; report additions now receive a schema minor, interpretation-breaking report changes receive a schema major, Diagnostic codes cannot be renamed or semantically reused without a breaking report version, and ordering tuples are incomparable across opaque policy IDs.

Added a release-review matrix and a deterministic version check covering `moon.mod`, CLI output, JSON Schema constants, a generated current report, renderer-conformance artifacts, and the compatibility consumer policy. Clarified that the compatibility corpus's unknown additive `1.0` field tests tolerant parsing rather than permission for a new producer to retain an old schema identity.
