# ISS-002: Make style precedence independent of attribute order

## Metadata
- Type: bug
- Status: closed

- Created: 2026-07-13
- Updated: 2026-07-14

## Description
`mizchi/svg@0.2.1` applies presentation attributes and inline `style` in XML attribute order. The equivalent rects `<rect style="fill:red" fill="blue">` and `<rect fill="blue" style="fill:red">` therefore resolve to blue and red respectively, although inline style should win in both cases. The declared-fact layer correctly normalizes both sources to the same effective inline declaration, so relying on the current renderer without a guard can make formatting-only attribute reordering alter Rendered Evidence or can hide the renderer divergence behind a false complete equality result.

Runtime reproduction on 2026-07-13 printed `0,0,255,255` for the style-first input and `255,0,0,255` for the style-last input.

## Design
Establish a conformance boundary for presentation-attribute versus inline-style precedence. `mizchi/svg@0.2.1` remains the latest release and upstream PR #4 remains open, so privately normalize only the renderer-input copy: when the complete supported inline declaration parser proves an overlap, replace the conflicting presentation attribute value with the same effective inline value before renderer parsing. Preserve the original source for Source Semantics, Source Spans, Changed Facts, Diagnostics, HTML, and resource admission. Retain the existing guard whenever the style declaration is incomplete or unsupported.

Route every production parse used for computed or rendered evidence through the adapter. Version the new adapter in `renderer_id`, advance the renderer conformance profile because its accepted guard set changes, and keep historical identities valid under the unchanged Structured Report field meanings.

## Acceptance Criteria
- [x] A regression test proves that reordering conflicting `style` and presentation attributes does not change Computed Appearance or Rendered Evidence.
- [x] The two inputs produce no Source Semantics Atomic Difference because their effective declared facts are identical.
- [x] The comparison engine does not report `complete` equality while its renderer produces different pixels for the two semantically equivalent inputs.
- [x] The chosen upstream fix, private normalization, or temporary coverage Diagnostic is documented with its conformance limitations.
- [x] Relevant MoonBit checks and tests pass.
