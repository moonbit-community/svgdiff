## Destination

Produce an implementation-ready redesign specification for the self-contained HTML Diff Report. The specification must define its audience, information architecture, visual-semantic classification, magnitude presentation, ordering, review controls, localization interaction, exact mapping to Structured Report evidence, and any minimal report-contract additions required by the accepted experience.

## Notes

- This map originally planned decisions only. The user later authorized the production HTML implementation in ISS-184; no Structured Report schema change was included.
- The primary interactive user is a human reviewer. A non-multimodal Agent consumes Structured Report JSON or Agent Projection evidence and must not depend on visual layout, color, or hover state.
- The default browsing unit is a Visual Event. Every owning Atomic Difference remains available inside that event.
- The HTML remains a projection of Structured Report evidence and may not independently derive semantic differences, calibrated severity, visibility, total ordering, or unique causality.
- Every session should consult `CONTEXT.md`, `docs/core-model.md`, `docs/impact-assessment.md`, `docs/agent-report-guide.md`, and ADR 0002. Use the `grilling` and `domain-modeling` skills for semantic decisions and the `prototype` skill for the interaction prototype.
- The local Markdown tracker represents child tickets with `Parent`, blocking with `Depends on`, claims with `Assignee`, and Wayfinder types with `wayfinder:<type>` labels.

## Decisions so far

- [Classify events without collapsing evidence dimensions](ISS-176.md) — Group Visual Events by measured-nonzero, not-computed, and measured-zero rendered outcomes while keeping Computed Relation, Domain Family, exact domain, and evidence availability as separate child facets.
- [Present magnitude without inventing severity](ISS-177.md) — Preserve five named magnitude channels, policy-bounded comparison, explicit availability, dual-layer numeric values, and absolute-scale graphics with a two-axis uncalibrated Impact Map.
- [Choose the localization surface for both previews](ISS-178.md) — Separate typed side footprints from observed or conservative outcome surfaces, target exact changed-pixel masks, preserve Event ownership, and stop at explicit unlocalized states instead of guessing.
- [Define the Visual Event card information hierarchy](ISS-179.md) — Use five question-driven layers with compact Event summaries, complete visible child inventories, evidence ownership, a compact overview, and deterministic progressive disclosure without hidden limitations.
- [Fix the boundary between report facts and HTML projection](ISS-181.md) — Keep review organization in a versioned projection and restrict report growth to canonical localization, measurement availability, and missing Diagnostic references with explicit legacy degradation.
- [Define review-control and selection semantics](ISS-180.md) — Use hierarchical Review Marks, one Event-owned localization selection, visibility-only filters, independent disclosures, session-only state, and synchronized preview navigation with orthogonal controls.
- [Prototype the event-centered review workflow](ISS-182.md) — Closed without retaining a throwaway artifact after the user chose to proceed directly to production.
- [Define acceptance for the redesigned HTML report](ISS-183.md) — Fix evidence-preservation, interaction, accessibility, hostile-source, partial/empty, and compatibility gates for production.
- [Implement the event-centered production HTML report](ISS-184.md) — Replace the current domain-first sidebar with the accepted review workflow and executable browser acceptance.

## Out of scope

- Implementing the deferred Structured Report schema additions for typed side footprints, exact observed masks, canonical Measurement Availability, and missing owned Diagnostic references.
- Introducing calibrated severity or visibility labels before the recorded Impact recalibration prerequisites are satisfied.
- Replacing canonical JSON or Agent Projection with HTML DOM as an Agent protocol.
- Selecting a frontend framework or producing pixel-perfect visual styling.
- Expanding SVG comparison coverage, including deferred font and dynamic-content semantics.
